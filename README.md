# SPR — робот сбора спреда для Bybit (бумажная торговля)

Маркет-мейкинговый робот для линейных USDT-перпетуалов Bybit: анализирует все пары,
отбирает подходящие, котирует обе стороны стакана мейкерскими лимитками, торгует
бумажно (симуляция исполнения по публичному потоку сделок), пишет всё в базу, а
аналитический контур разбирает каждую сделку, предлагает изменения параметров и
подбирает их автоматически по записанным данным.

```
┌─────────────── Rust: core/ (бинарь spr) ────────────────┐   ┌────── Python: analytics/ ──────┐
│ Bybit WS ─► движок (один поток):                          │   │ analyze   круги, markout,      │
│   стакан → статистика → фильтр пар → котировки            │   │           диагностика → БД      │
│   → бумажная биржа → портфель → риск                      │──►│ pairs     скоринг пар           │
│ поток записи: SQLite (WAL) + бинарные файлы стакана/сделок│   │ optimize  Optuna × spr replay  │
│ spr sim (синтетика), spr replay (прогон по записи)        │   │ dashboard FastAPI + Plotly     │
└───────────────────────────────────────────────────────────┘   └────────────────────────────────┘
                        config/strategy.toml ◄── overrides.json, symbols.json (горячая перезагрузка)
```

Ключевой принцип: **одна и та же логика** (стратегия, бумажная биржа, портфель) работает
вживую, в синтетической симуляции и в replay по записанным данным. Оптимизатор проверяет
ровно тот код, который торгует. Дашборд — отдельный процесс, читает только SQLite и никак
не влияет на скорость ядра.

## Требования

- Rust 1.75+ (`cargo`), Python 3.10+.
- Сетевой доступ к `api.bybit.com` (REST) и `stream.bybit.com` (WebSocket).
  **Bybit блокирует IP из США** (403 от CloudFront): с такого адреса REST не работает,
  а WebSocket-стримы работают. Ядро умеет брать список инструментов из файла
  (`spr symbols --out`), см. ниже.

## Быстрый старт без сети

```bash
# 15 минут синтетического рынка, 30 пар, максимально быстро (speed 0)
./core/target/release/spr sim --symbols 30 --duration-secs 900 --speed 0

# разбор сделок и рекомендации
python -m spr_analytics analyze

# дашборд: http://localhost:8000
uvicorn spr_analytics.dashboard.app:app --port 8000

# автономный цикл: диагностика и применение изменений без участия человека
python -m spr_analytics auto --apply
```

`--speed 1` гонит синтетику в реальном времени (удобно смотреть дашборд вживую),
`--toxicity 0..1` задаёт долю информированного потока, `--seed` — воспроизводимость.

## Живой запуск (paper trading на реальном потоке Bybit)

```bash
# 1. список инструментов (и сохранить его в файл на случай, если REST недоступен)
./core/target/release/spr symbols --out config/instruments.json

# 2. торговля всеми парами, Ctrl-C для остановки
./core/target/release/spr run

# варианты
./core/target/release/spr run --symbols BTCUSDT,ETHUSDT      # только эти пары
./core/target/release/spr run --max-symbols 150               # 150 самых оборотистых
./core/target/release/spr run --duration-secs 3600            # остановиться через час
./core/target/release/spr run --instruments-file config/instruments.json   # REST закрыт
```

Если REST недоступен, ядро само возьмёт `config/instruments.json` рядом с конфигом.
Фильтр по обороту 24ч в этом случае отключён до первого успешного запроса тикеров.

Ядро раз в 10 секунд пишет строку состояния в stderr, а по окончании печатает
JSON-сводку в stdout.

## Как это работает

### Ядро (core/src)

| Модуль | Что делает |
|---|---|
| `bybit/ws.rs` | несколько WebSocket-соединений (`topics_per_connection`), подписки батчами, ping каждые 20 с, реконнект с backoff, парсинг JSON в рабочих задачах tokio |
| `bybit/rest.rs` | `instruments-info` (пагинация), `tickers` (оборот 24ч), файл-фолбэк |
| `engine.rs` | единый цикл: событие рынка → стакан → статистика → бумажная биржа → перекотировка; раз в секунду: фильтр пар, top-N активных, риск, снимки, перезагрузка конфига |
| `book.rs` | локальный стакан в целых тиках, snapshot/delta, починка пересечённого стакана |
| `stats.rs` | посекундные сэмплы: медиана спреда, волатильность (std лог-доходностей × √60), сделок/мин, дисбаланс потока |
| `eligibility.rs` | deny/allow → свежесть → оборот → прогрев → спред → сделки → спред/вола; score = спред·√(сделок/мин)/(1+вола) |
| `strategy.rs` | `compute_quotes`: чистая функция состояния → котировки (см. ниже) |
| `paper.rs` | бумажная биржа: латентность выставления и отмены, очередь впереди, post-only, исполнение по публичным сделкам и движению BBO |
| `portfolio.rs`, `risk.rs` | позиции по средней цене, PnL, просадка; дневной лимит убытка (kill-switch), валовая экспозиция, число позиций |
| `store.rs`, `recorder.rs` | поток записи: SQLite батчами, бинарные файлы стакана и сделок по дням |
| `replay.rs`, `simfeed.rs` | прогон по записи; синтетический рынок с режимами тренда, токсичным потоком и импактом сделок |

### Логика котирования

Ключевая идея: котировать не вокруг середины спреда, а вокруг **справедливой цены**. Широкий
спред на неликвидной паре существует потому, что тот, кто просто встаёт в лучшую цену,
исполняется перед движением против себя. Справедливая цена собирается из трёх сигналов:
дисбаланс объёмов на лучших уровнях (`imbalance_weight`), дисбаланс потока сделок за последние
секунды (`flow_weight`) и отклонение цены той же монеты на ликвидной площадке
(`ref_weight`, см. «Референсные потоки»). Сторона, которую справедливая цена уводит глубже
`max_lean_ticks` от лучшего уровня, не котируется.

1. Стоп по движению: mid ушёл против позиции на `stop_loss_bps` → немедленный выход
   (`stop_loss_mode`: рыночным или на тик внутрь), не дожидаясь `max_hold_secs`.
2. Позиция старше `max_hold_secs` → только выход (`stale_exit_mode`).
3. Волатильность выше `max_vol_bps` → только пассивный выход из открытой позиции.
4. Требуемый спред = `max(min_spread_bps, 2·комиссия_мейкера + min_edge_bps)`.
   Режим `inside` (по умолчанию) — стоять строго внутри спреда вокруг справедливой цены,
   первыми в очереди, сохраняя не меньше `inside_spread_frac` полуспреда; если места внутри
   нет, сторона не котируется, в чужую очередь мы не встаём. `improve` — на тик внутрь, если
   спред позволяет, иначе в лучшую цену; `join` — в лучшую цену. Живые данные показали, что
   исполнения из чужой очереди на неликвидных парах теряют 5–16 bps уже через секунду, а
   исполнения внутри спреда нейтральны, отсюда выбор `inside` по умолчанию.
5. Справедливая цена: `fair = mid + (imbalance_weight·дисбаланс_стакана + flow_weight·дисбаланс_потока)·полуспред + ref_weight·отклонение_референса`.
   Каждая котировка держит не меньше половины требуемого спреда от `fair`; если для этого её
   надо отодвинуть глубже `max_lean_ticks`, сторона снимается.
6. Скос по инвентарю: обе котировки сдвигаются против позиции на
   `inventory_skew_bps · (позиция / max_position_notional_usd)`, целыми тиками, не пересекая рынок.
7. Жёсткие блокировки стороны: дисбаланс потока выше `toxicity_imbalance`; референс уже ушёл
   дальше `ref_block_bps`.
8. Размер `order_notional_usd / mid`, округление вниз до лота; у лимита позиции — только сторона
   выхода; выпавший из активного набора символ — только выход (`reduce_only`).

Ядро само измеряет **markout** после каждого своего исполнения (движение mid через
`markout_horizon_secs`) и ведёт по символу скользящее среднее. Символ со средним markout'ом
хуже `−max_adverse_markout_bps` (после `min_markout_samples` исполнений) выпадает из активного
набора как `toxic_flow`, а положительный опыт поднимает его в рейтинге. Это самообучение прямо
в ядре, без участия Python.

### Референсные потоки (`[reference]`)

Неликвидный перпетуал на Bybit следует за той же монетой на ликвидной площадке с задержкой в
сотни миллисекунд. Ядро подписывается на лучшие цены той же монеты у провайдеров из
`providers` (в порядке приоритета: `binance_futures`, `binance_spot`, `bybit_spot`; символы,
которых на площадке нет, просто молчат), ведёт сглаженный базис (наш mid − референс) и считает
отклонение `(референс + базис − наш mid)` в bps. Отклонение сдвигает справедливую цену
(`ref_weight`) и блокирует сторону, которую вот-вот снесут (`ref_block_bps`). Референс
записывается вместе со стаканом (`run{id}_ref.bin`), поэтому replay и оптимизатор видят его
так же, как живой движок. Сигнал при выставлении сохраняется в каждом исполнении
(`fills.ref_dev_bps`, `fills.imbalance`), а дашборд показывает markout'ы «против нас / нейтрально /
за нас» — так видно, работает ли референс на конкретных парах.

### Бумажное исполнение

Ордер активируется через `latency_ms`, отмена тоже действует через `latency_ms` (в это время
ордер может исполниться). При активации ордер, пересекающий рынок, отклоняется (post-only).
Очередь впереди = показанный размер на нашей цене (0, если мы внутри спреда); уменьшение
показанного размера уменьшает очередь. Публичная сделка на нашей цене с нужной стороной тейкера
сначала съедает очередь, остаток исполняет нас; сделка сквозь нашу цену или движение BBO сквозь
неё исполняют остаток. Это консервативная модель: реальные исполнения обычно не хуже.

## Данные

- `data/spr.db` — SQLite (WAL). Таблицы: `runs`, `fills`, `orders`, `symbol_stats`,
  `pnl_snapshots`, `position_state`, `events`, `param_versions`; аналитика пишет
  `recommendations`, `optimizer_runs`, `pair_scores`.
- `data/md/YYYYMMDD/run{run_id}_bbo.bin` (48 байт на запись), `run{run_id}_trd.bin` (32 байта),
  `run{run_id}_symbols.json` (метаданные инструментов). Python читает их через `numpy.fromfile`
  (`spr_analytics.md`). BBO пишется не чаще `bbo_min_interval_ms` на символ; при 250 мс и
  нескольких сотнях пар это порядка 1–3 ГБ в день. Старые дни удаляет
  `python -m spr_analytics clean --keep-days 14`.

## Аналитика

```bash
python -m spr_analytics analyze [--run-id N] [--min-n 30] [--apply]
python -m spr_analytics pairs   [--hours 24] [--allow-top 40]
python -m spr_analytics optimize --from 2026-09-25T08:00 --to 2026-09-25T20:00 \
        [--symbols A,B] [--trials 40] [--apply]
python -m spr_analytics report
python -m spr_analytics clean --keep-days 14
```

**analyze** также раскладывает markout'ы по позиции в очереди (очередь впереди / размер ордера:
0, <1x, 1–3x, >3x), по стороне, по часу UTC и по сигналу референса при выставлении. Это
отвечает на вопрос «где именно нас переезжают»: если убыточны только входы из хвоста очереди,
нужен приоритет (`quote_mode=improve`, правило `back_of_queue`); если только одна сторона или
только определённые часы, это видно сразу. Те же таблицы есть на вкладке «Рекомендации».

**analyze** сводит исполнения в круги (FIFO по лотам: цена входа/выхода, удержание,
захваченный спред в bps против котируемого, комиссии), считает markout'ы (движение mid через
1/5/30/60 с после каждого исполнения; отрицательные = нас переехал информированный поток) и
прогоняет правила диагностики. Каждое правило превращает статистически подтверждённую
проблему в конкретное изменение параметра:

| Правило | Признак | Предложение |
|---|---|---|
| `adverse_selection` | markout 5 с после входа < −0.5 × полуспреда | `min_spread_bps` ×1.25, `toxicity_imbalance` −0.1 |
| `low_fill_ratio` | исполняется < 5 % ордеров при очереди > 3 размеров ордера | `quote_mode=improve` либо `min_requote_ms` ×2 |
| `stale_holding` | p90 удержания > 0.8·`max_hold_secs`, принудительные выходы убыточны | `max_position_notional_usd` ×0.7, `inventory_skew_bps` ×1.5 |
| `losing_symbol` | ≥ 20 кругов, итог < 0, прибыльных < 45 % | символ в deny |
| `spread_leakage` | реализованный спред < 0.5 × котируемого | `min_spread_bps` ×1.2 |
| `fee_heavy` | комиссии > 50 % валового | `order_notional_usd` ×1.5, `min_edge_bps` +1 |
| `too_few_trades` | < 2 кругов в час на активный символ | `min_spread_bps` ×0.85 (глобально) |

Рекомендации пишутся в таблицу `recommendations` и видны на дашборде. С флагом `--apply`
предложенные значения записываются в `config/overrides.json` (по символу, `"*"` — для всех),
deny-список — в `config/symbols.json`; ядро подхватывает изменения в течение 5 секунд, плохие
значения отклоняются валидацией и не применяются.

**auto** — автономный режим, который делает всё это сам:

```powershell
python -m spr_analytics auto --apply                      # analyze каждые 10 мин, pairs раз в час
python -m spr_analytics auto --apply --optimize-every 360 --optimize-hours 6 --trials 30
```

Каждые `--analyze-every` минут прогоняет диагностику по текущему запуску и пишет рекомендации;
с `--apply` сразу записывает предложенные значения в `overrides.json` / `symbols.json` (ядро
подхватывает за 5 секунд). Защита от «раскачки»: один параметр одного символа меняется не чаще
`--cooldown` (60 мин), а после каждого изменения диагностика смотрит только на сделки,
совершённые после него, то есть каждое изменение оценивается на свежих данных. Раз в
`--pairs-every` минут пересчитывает скоринг пар, раз в `--optimize-every` минут (по умолчанию
выключено) запускает оптимизатор по последним `--optimize-hours` часам записи для символов,
которые реально торговались. Состояние хранится в `config/auto_state.json`. Без `--apply`
режим только советует, а решения остаются за вами.

**pairs** считает офлайн-score пар по истории `symbol_stats` (медиана спреда, сделки/мин,
волатильность) с поправкой на реально заработанное и пишет `config/symbols.json`:
`scores` (усредняются с онлайн-score в ядре), `deny` (стабильно убыточные), `allow`
(если задан `--allow-top N`, ядро котирует только эти пары).

**optimize** — самообучение. Optuna (TPE) подбирает параметры стратегии, прогоняя
`spr replay` по записанным данным периода: первые 70 % периода — обучение, остальные 30 % —
проверка. Целевая функция `net_pnl − λ·max_drawdown − μ·avg_abs_inventory` (по умолчанию
λ=0.5, μ=0.01). Найденные параметры применяются (`--apply`) только если на проверочном
отрезке они лучше текущих не менее чем на `--min-improvement` (защита от переобучения).
Результат — в таблице `optimizer_runs`. Replay 15 минут рынка для 30 пар занимает ~0.1 с,
так что сотни попыток — это минуты.

Ручной прогон с любыми параметрами:

```bash
./core/target/release/spr replay --from 2026-09-25T08:00 --to 2026-09-25T12:00 \
    --symbols SIM011USDT --params-json '{"min_spread_bps": 15, "quote_mode": "improve"}'
```

## Дашборд

```bash
uvicorn spr_analytics.dashboard.app:app --port 8000   # http://localhost:8000
SPR_DB=/path/to/spr.db uvicorn ...                     # другая база
```

Вкладки: обзор (капитал, экспозиция, накопленный результат по кругам, распределение bps за
круг), пары (последний снимок статистики по всем символам, фильтр, причина отказа, позиция),
сделки (круги и исполнения), рекомендации и скоринг пар, оптимизатор (запуски и текущие
параметры ядра), события. Обновление по таймеру (3/10/30 с), выбор запуска.
Plotly отдаётся из установленного python-пакета `plotly` (работает без интернета).

## Параметры (`config/strategy.toml`)

| Секция / параметр | Смысл |
|---|---|
| `exchange.symbols`, `max_symbols` | ограничить список пар (пусто = все) |
| `exchange.orderbook_depth` | 1 (10 мс), 50 (20 мс), 200/500 (100 мс) |
| `fees.maker_rate`, `taker_rate` | комиссии (VIP0: 0.02 % / 0.055 %) |
| `paper.latency_ms`, `initial_equity_usd` | латентность бумажной биржи, стартовый капитал |
| `strategy.*` | все параметры котирования — их же подбирает оптимизатор |
| `strategy.imbalance_weight`, `flow_weight`, `ref_weight` | веса сигналов справедливой цены |
| `strategy.ref_block_bps`, `max_lean_ticks` | блокировка стороны по референсу и по глубине наклона |
| `strategy.stop_loss_bps`, `stop_loss_mode` | стоп по движению против позиции |
| `eligibility.markout_horizon_secs`, `max_adverse_markout_bps`, `min_markout_samples` | онлайн-markout в фильтре пар |
| `reference.*` | провайдеры опережающих площадок, устаревание, сглаживание базиса |
| `eligibility.*` | пороги фильтра пар, окно, `max_active_symbols`, `refresh_secs` |
| `risk.*` | дневной лимит убытка, валовая экспозиция, число позиций |
| `recording.*` | запись стакана: вкл/выкл, коалесценция, `all`/`eligible` |
| `storage.*` | пути к БД и файлам, периодичность снимков |

`strategy.toml`, `overrides.json` и `symbols.json` перечитываются на лету по mtime.
Изменения `exchange.*` и `storage.*` требуют перезапуска.

## Ограничения и что дальше

- Бумажная модель не видит скрытую ликвидность и айсберги; очередь для уровней глубже
  лучшего оценивается по размеру лучшего уровня (для `orderbook.1`).
- Комиссии фиксированные из конфига; funding не учитывается (позиции держатся секунды).
- Для перехода к реальной торговле нужен приватный WS/REST (ключи, подпись, `order.create`),
  сверка позиций и лимиты по API-запросам — движок к этому готов: заменить `PaperExchange`
  на реальный исполнитель с тем же интерфейсом (`place`/`cancel`/`fills`/`done`).
