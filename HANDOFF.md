# HANDOFF: робот сбора спреда (SPR) для Bybit

Состояние проекта после второй сессии. Инструкция по запуску и описание системы — в
`README.md`; здесь история решений, что проверено, что нет, и что делать дальше.

## 1. Исходная постановка задачи (дословно от пользователя)

> я хочу написать робота для сбора спреда в стакане. давай возьмем для примера биржу bybit,
> напишем сам механизм, анализировать будем вначале все пары, потом возможно их как-то
> ограничим, я надеюсь тут ты тоже позже предложишь механизм для определения какие пары
> подходят для торговли, а какие нет в данный момент. торговать будем пока бумажно для
> проверки работоспособности. но самое главное и самое важное это механизм анализа всех
> сделок которые мы совершаем и если они убыточны или просто возможно было бы сделать эту
> сделку лучше, то алгоритм должен сам либо предлагать какие изменения надо сделать, либо
> обучаться сам для улучшения своего алгоритма. средой разработки должна быть среда где
> можно создать достойный визуал, а самое главное чтобы это не влияло на скорости расчета
> и отправки/получения данных с биржи. если необходимо перед написанием можешь задать мне
> уточняющие вопросы

### Ответы пользователя на уточняющие вопросы

| Вопрос | Ответ |

### Известная проблема, исправленная после первого живого прогона пользователя

На реальном прогоне (777 пар) запись в базу остановилась в момент запуска `analyze`/`auto`
из Python: поток записи ядра при ошибке транзакции (в т.ч. SQLITE_BUSY, таймаут был 5 с)
завершался, а ядро продолжало торговать, ничего не сохраняя. Исправлено: `busy_timeout` 30 с
с обеих сторон, поток записи повторяет батч до 5 раз и никогда не выходит из-за ошибки
записи, при мёртвом потоке ядро пишет ERROR раз в минуту, дашборд подсвечивает «нет записи
в БД», если снимок старше минуты при идущем запуске. Проверено удержанием блокировки 8 с
из Python во время симуляции в реальном времени.

### Сессия 2, вторая часть: почему стратегия теряла и что добавлено

Первый живой прогон пользователя (777 пар, ~40 мин): 68 кругов, 26 % прибыльных, −20 bps за
круг при котируемом спреде 12–20 bps, комиссии 1.5 из −3.4 USDT. Диагноз: неблагоприятный
отбор — исполнения происходят перед движением против нас, комиссии вторичны. Добавлено:

- **Справедливая цена** в `strategy.rs`: дисбаланс стакана, дисбаланс потока и отклонение
  референса сдвигают цену, вокруг которой котируем; сторона, уходящая глубже `max_lean_ticks`,
  снимается; `ref_block_bps` блокирует сторону по референсу. `Quotes.fair_shift_bps` для отладки.
- **Стоп по движению** `stop_loss_bps`/`stop_loss_mode` (Purpose::StopLoss в fills).
- **Онлайн-markout в ядре**: `SymbolState.experience` (EWMA ~30 исполнений), пишется в
  `symbol_stats.markout_bps/markout_n`, участвует в `eligibility` (`toxic_flow`, коррекция score).
- **Референсные потоки**: `binance.rs` (combined bookTicker, futures/spot), `bybit/ws.rs` в
  режиме Reference (depth-1 мини-стакан, подписки по одному символу), приоритет провайдеров,
  базис EWMA, устаревание; запись `run{id}_ref.bin`, чтение в replay (`MdEvent::Ref`), синтетика
  с лагом (`--ref-lag-ms`) и арбитражным потоком.
- **Миграция БД**: `store::migrate` добавляет колонки `fills.ref_dev_bps/imbalance`,
  `symbol_stats.markout_bps/markout_n/ref_dev_bps` в существующую базу.
- **Аналитика**: разрезы markout'ов (очередь, сторона, час, сигнал референса), правило
  `back_of_queue`, скоринг пар с учётом markout'ов ядра, новые параметры в пространстве
  оптимизатора, `/api/markouts` и панель на дашборде, `md.load_ref/ref_series`.

Проверка на синтетике (40 пар, 30 мин, токсичность 0.9, лаг 1 с): старая логика −4.34 USDT,
markout −2.87 bps; новая +2.20 USDT, markout −0.75 bps, просадка 3.5 против 6.4. Replay по
записи с референсом воспроизводит результат. 33 Rust-теста, 5 pytest.

### Второй живой прогон пользователя (4.4 ч после обновления) и реакция

145 кругов, 41 % прибыльных, −7.4 bps за круг (было 26 % и −20), валовый −3.9, комиссии
5.1. Таблицы markout'ов дали диагноз: входы **из чужой очереди** теряют 5–16 bps уже через
секунду (все корзины «<1x», «1–3x», «>3x»), входы **внутри спреда** (очередь 0) нейтральны.
Референс почти не участвовал: 93 из 124 входов «нейтрально», потому что на мелких парах
референсная котировка обновляется реже 3 с и считалась устаревшей. Активных пар 0–2 из 777
из-за порога 3 сделки/мин.

Сделано: режим `quote_mode = "inside"` (по умолчанию) — котировать только строго внутри
спреда вокруг справедливой цены, сохраняя `inside_spread_frac` (0.8) полуспреда, в чужую
очередь не вставать; `min_trades_per_min` 3 → 1; `reference.stale_ms` 3 с → 30 с; правила
`back_of_queue`/`low_fill_ratio` советуют `inside`, новое `inside_too_tight` расширяет долю
спреда; оптимизатор перебирает режим и долю; открытые рекомендации старых запусков
закрываются новым анализом.

Синтетика (40 пар, 30 мин): на токсичном рынке (0.9, лаг 1 с) inside 0.8–0.9 даёт +1…+6 USDT
против +1.3 у join с моделью и −6 у исходной логики; на спокойном рынке (0.5) join выигрывает
(+83 против +45), потому что там чужая очередь не токсична. Реальный рынок пользователя по
данным токсичный, поэтому умолчание inside; окончательный выбор режима и доли — за
диагностикой и оптимизатором на живых данных.

## 4. Что НЕ проверено (сделать на машине с доступом к REST Bybit)

- `spr symbols` и `spr run` с реальным `instruments-info`/`tickers`: из облачного контейнера
  (IP США) REST Bybit отдаёт 403 CloudFront «доступ из вашей страны заблокирован»; WebSocket
  при этом работает. Парсер REST покрыт юнит-тестом на реальном формате ответа.
- Долгий живой прогон на всех парах (несколько сотен символов, десятки соединений):
  нагрузка, реконнекты, объём записи (оценка 1–3 ГБ/день при 250 мс коалесценции).
- Реальные исполнения на неликвидных парах: в живом smoke-тесте были только мажоры, ни
  одной котировки не выставлялось (спреды ниже порога). Первое, что стоит сделать:
  `spr run --duration-secs 3600`, затем `analyze` и посмотреть на markout'ы.

## 5. Ключевые решения (и почему)

- **Одна логика для live / sim / replay**: `Engine` получает `MarketEvent` и `now`; вживую
  `now` = системные часы, в replay — время записи. Оптимизатор гоняет ровно торгующий код.
- **Ядро однопоточное по состоянию**, парсинг JSON в задачах tokio, запись в отдельном потоке
  через unbounded-канал: движок никогда не ждёт диск и не разбирает JSON.
- **Дашборд не трогает ядро**: отдельный процесс, SQLite в WAL-режиме читается параллельно с
  записью. Plotly отдаётся из python-пакета (в контейнере CDN был закрыт).
- **Цены в целых тиках**, размеры округляются вниз до лота, `min_notional` проверяется.
- **Горячая перезагрузка** трёх файлов по mtime раз в 5 с; неверные override'ы отклоняются
  валидацией, старые параметры остаются; каждая версия параметров пишется в `param_versions`
  и помечает исполнения (`fills.param_version`), так что аналитика может сравнивать версии.
- **Перекотировка**: ордер снимается, если желаемая цена отличается на тик, поменялась цель
  (entry/exit) или флаг taker; новый ставится только после завершения отмены (латентность),
  чтобы не удваивать экспозицию. Не чаще `min_requote_ms`, ордера старше `max_order_age_ms`
  снимаются. На синтетике это даёт ~5 % исполненных ордеров — много отмен; для реальной биржи
  это нормально для мейкера, но rate-limit'ы надо будет учитывать.
- **TLS**: `tokio-tungstenite` и `reqwest` собраны с `rustls-tls-native-roots`, чтобы
  доверять системному хранилищу сертификатов (корпоративные прокси, как в этом контейнере).
- **Инструменты из файла**: `spr symbols --out config/instruments.json` на машине с REST, ядро
  берёт файл, если REST недоступен. `config/instruments.json` в `.gitignore`.
- **Круги в аналитике считаются FIFO по лотам** (450 на 663 исполнения), в ядре — по выходу в
  ноль (187). Это разные единицы: в ядре — для win-rate в JSON-сводке, в аналитике — для
  сравнения цены входа/выхода и удержания.

## 6. Факты по Bybit V5 (проверено на живом потоке)

- Public WS linear: `wss://stream.bybit.com/v5/public/linear`; `{"op":"ping"}` каждые 20 с,
  ответ `{"success":true,"ret_msg":"pong","op":"ping"}`; подписка
  `{"op":"subscribe","req_id":"...","args":["orderbook.1.BTCUSDT","publicTrade.BTCUSDT"]}`,
  ответ `{"success":true,"ret_msg":"subscribe","op":"subscribe"}`.
- `orderbook.{depth}.{symbol}`: `{"topic","type":"snapshot"|"delta","ts","data":{"s","b":[["p","q"]],"a":[...],"u","seq"},"cts"}`;
  `q=="0"` — удалить уровень; `u==1` или `snapshot` — сброс стакана; для L1 при отсутствии
  изменений snapshot повторяется каждые ~3 с.
- `publicTrade.{symbol}`: `{"topic","type":"snapshot","ts","data":[{"T","s","S":"Buy"|"Sell" (тейкер),"v","p","L","i","BT"}]}`.
- REST `GET /v5/market/instruments-info?category=linear&limit=1000&cursor=`:
  `symbol, contractType ("LinearPerpetual"), status ("Trading"), baseCoin, quoteCoin,
  priceFilter.tickSize, lotSizeFilter.{minOrderQty,maxOrderQty,qtyStep,minNotionalValue}`,
  `nextPageCursor`. `GET /v5/market/tickers?category=linear`: `symbol, turnover24h, ...`.
- WS Trade API (`/v5/trade`) и testnet из контейнера США тоже закрыты; приватный стрим
  `/v5/private` открывается (без авторизации только pong).

## 8. Как собрать и проверить

```bash
cd core && cargo test && cargo build --release && cd ..
./core/target/release/spr sim --symbols 30 --duration-secs 900 --speed 0   # без сети
python3 -m venv .venv && . .venv/bin/activate && pip install -e analytics
python -m pytest analytics/tests
python -m spr_analytics analyze && python -m spr_analytics pairs
uvicorn spr_analytics.dashboard.app:app --port 8000
```

Сетевые хосты: `api.bybit.com` (REST), `stream.bybit.com` (WS), для документации
`bybit-exchange.github.io`.
